## 有效未决问题（要处理）

1. **mmap 关闭误伤 dense（P0，Chatgpt 指出）**：`init_mappings` 检测 `n_expert>0` 就整个模型
   `use_mmap=false` → dense（非 `_exps`）也离开 mmap、普通 read 物理读入。决定大模型内存上限。
   **待验证**：deepseek dense_total_bytes 到底多大（看 GGUF 即知）。若 dense 读入量 + 池预算 > RAM，
   "低 RAM 跑超大 MoE"目标不成立——需要 dense 保持 mmap（只 expert 离开）。
2. **scheduler 单线程 + 同步阻塞读（P1）**：`read_expert_sync` 阻塞，跨专家 miss 串行。正解：
   nodejs 风格——scheduler 只调度 + 发异步读（IOCP in-flight 并发）+ 完成回调。即 B22 的
   io_uring/io_submit fallback 方向。
3. **驱逐忙等无超时（P1）**：`while (refcount != 0) yield()` 无限自旋。正常不触发（EVICTING 阻止
   新 pin），触发 = pin/unpin 泄漏（delegate 异常路径等）。加超时 + 日志（L/E + refcount）。
4. **驱逐打分魔数（P2）**：`score = 0.5*freq + 0.5*(1 - gen/1e9)`，`gen << 1e9` 导致 recency 项
   区分度≈0，驱逐实际只看 freq。**方向**：修 recency 归一化 + 动态 α（用户想法：整体实时 hit rate，
   初始 = pool/total，hit 升 → 加大 freq 权重，降 → 加大 LRU 权重）。
5. **`_exps` 专家连续切片假设**：只在加载时（read_plan 计算），运行时用显式偏移。v1/原版 GGUF
   保证成立；v2 用 sections 显式块偏移、不依赖该假设。
6. **异常 throw → server 崩溃风险**：moe_loader 直抛，server 常驻进程加载失败可能挂掉（现有
   try-catch 在 route_b_setup，链路待审）。
7. **v1/v2 双套逻辑维护成本**：引擎按 `stream_moe.layout` 自动选（v1 切片 / v2 sections）。
   文档需明确"何时用 v1 / 何时转 v2"。
8. **shexp（shared expert）未覆盖**：`sub_tensor_names` 无 `_shexp`，保持默认后端（文档要注明）。
